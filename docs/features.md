# Функциональность Transfer Service

Водитель публикует поездку, пассажир ищет её по городам и бронирует места. Клиент получает JWT при входе и передаёт его в заголовке `Authorization: Bearer <token>` для защищённых маршрутов.

## Маршруты

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `GET /health` | Публичный | `200` и статус HTTP-сервера |
| `POST /api/v1/users/` | Публичный | `201` и профиль новой учётной записи с ролью `driver` или `passenger`. Хеш пароля исключён из ответа |
| `POST /api/v1/users/login` | Публичный | `200` и объект с полем `token`. JWT действителен 24 часа |
| `GET /api/v1/trips` | Публичный | `200` и список поездок. Опциональные параметры `from` и `to` фильтруют по подстроке без учёта регистра. У завершённых поездок заполнено `completed_at`. Ответ содержит имя, среднюю оценку и число оценок водителя |
| `POST /api/v1/trips` | Водитель | `201` и новая поездка. Идентификатор водителя берётся из JWT, все места изначально свободны |
| `POST /api/v1/trips/{id}/complete` | Водитель-владелец | `204` после завершения или при повторном запросе, `404` для чужой или отсутствующей поездки, `409` до времени отправления или пока не подтвердили прибытие все пассажиры с подтверждённой бронью |
| `GET /api/v1/trips/balance` | Водитель | `200` с заблокированной и доступной суммами в центах USD и списком поездок, готовых к завершению |
| `POST /api/v1/bookings` | Пассажир | `201` и заявка в статусе `requested`, `409` для завершённой поездки |
| `GET /api/v1/bookings/my` | JWT | `200` и все брони пользователя из JWT, включая отменённые. `paid` обозначает оплату через Stripe, `payment_available` — доступность Checkout |
| `DELETE /api/v1/bookings/{id}` | JWT, владелец брони | `204`, бронь получает статус `cancelled`, места возвращаются в поездку. Для брони вне действующего `requested` или `pending` возвращается `400` |
| `POST /api/v1/bookings/{id}/pay` | JWT, пассажир и владелец | `200` с URL Stripe Checkout, `404` для чужой или отсутствующей брони, `409` для недоступной к оплате брони, `503` при отключённой оплате |
| `GET /api/v1/bookings/driver` | Водитель | `200` со списком броней его поездок, именем и средним рейтингом пассажира |
| `POST /api/v1/bookings/{id}/decision` | Водитель-владелец поездки | `204` для действующей заявки после решения `approve` или `reject`. При отказе места возвращаются |
| `POST /api/v1/bookings/{id}/rating` | Водитель или пассажир завершённой брони | `204` после сохранения оценки от 1 до 5 и необязательного отзыва до 1000 символов, `409` если оценка уже оставлена или доступ к действию отсутствует |
| `POST /api/v1/bookings/{id}/arrive` | Пассажир-владелец | `204` после подтверждения прибытия или при повторном запросе, `404` для чужой брони, `409` до отправления или для неподтверждённой брони |
| `POST /api/v1/webhooks/stripe` | Подпись Stripe | `204` после обработки события, `400` при неверной подписи или некорректном событии |

Пустые списки возвращаются как `[]`. Проверка JWT выполняется в middleware. Роли водителя и пассажира для создания поездок и броней проверяют обработчики. При отмене принадлежность брони проверяет репозиторий.

Маршруты и middleware зарегистрированы в [cmd/api/main.go](../cmd/api/main.go). Тела запросов и правила валидации описаны в [internal/models](../internal/models). Сгенерированная спецификация доступна в [swagger.yaml](api/swagger.yaml).

## Жизненный цикл брони

1. Пассажир отправляет `trip_id` и положительное число мест в `seats`. Репозиторий блокирует строку поездки через `FOR UPDATE`, проверяет доступность мест и в одной транзакции уменьшает остаток и создаёт заявку в `requested`. Отсутствующая поездка даёт `404`, нехватка мест даёт `400`.
2. При ручной отмене репозиторий блокирует действующую бронь владельца в `requested` или `pending` и в одной транзакции обновляет статус и возвращает места. Повторная отмена возвращает `400`.
3. Воркер запускает проверку раз в минуту. Заявки в `requested` и брони в `pending` с истёкшими 15 минутами переходят в `expired` с возвратом мест в той же транзакции. Время считается по `bookings.created_at` в PostgreSQL.

4. Водитель может принять заявку и открыть 15-минутное окно оплаты или отклонить её с возвратом мест. Пассажир может открыть тестовый Stripe Checkout для своей действующей брони в `pending`. Сервер рассчитывает сумму по цене поездки и числу мест в центах USD. Повторный запрос использует тот же ключ идемпотентности Stripe.
5. API проверяет подпись вебхука `checkout.session.completed` и подтверждает только действующую бронь с совпадающей суммой. Повторная доставка для того же платежа сохраняет итоговое состояние. Если бронь уже отменена, просрочена или относится к завершённой поездке на момент обработки, API записывает полный тестовый возврат в PostgreSQL. Воркер повторяет запросы при сбоях и сверяет состояние возврата со Stripe. Места возвращает отмена или воркер. Оплаченную через Stripe бронь пассажир не может отменить через API.
6. После времени отправления пассажир с подтверждённой бронью нажимает «Я на месте». Водитель-владелец завершает поездку, когда хотя бы один пассажир подтвердил прибытие и получены подтверждения по всем подтверждённым броням. API показывает подтверждённые брони как `completed`, а оставшиеся `requested` и `pending` как `expired`. Воркер закрывает оставшиеся резервы и возвращает места при ближайшем запуске. Новые брони и оплаты для этой поездки недоступны.

7. До завершения поездки принятые платежи учитываются в заблокированной части внутреннего тестового баланса водителя. Завершение переносит их в доступную часть. Баланс отражает учёт в PostgreSQL. Реальные переводы и вывод через Stripe Connect требуют отдельной интеграции.

8. После завершения поездки каждый участник может один раз поставить другой стороне оценку от 1 до 5 за бронь. Средняя оценка водителя и число оценок доступны в публичном списке поездок. Средняя оценка пассажира и число оценок доступны только водителю, у которого есть его бронь. Текст отзыва виден его автору в истории брони. Водитель принимает решение вручную.

Ответы создания и списка содержат `created_at` из PostgreSQL. Доступность оплаты отражает список броней.

Запросы и границы транзакций находятся в [booking_repo.go](../internal/repository/booking_repo.go), цикл очистки — в [booking_worker.go](../internal/worker/booking_worker.go).
