# План фронтенда Transfer Service

Первый релиз фронтенда — вход по email и паролю в `frontend/`. Роль «Пассажир» или «Водитель» выбирается при регистрации на `/register`. Регистрация использует существующий `POST /api/v1/users/`. После создания аккаунта пользователь переходит к форме входа. Следующие экраны — поездки и бронирования. [Роадмап](roadmap.md) · [Дизайн](../DESIGN.MD)

## Стек и границы состояния

| Инструмент | Задача |
| --- | --- |
| Next.js App Router + TypeScript в строгом режиме | Маршруты, общий layout, серверный маршрут для проксирования входа |
| TanStack Query | Мутация входа без автоматических повторов. В следующих этапах — запросы и кэш серверных данных |
| Zustand | JWT и минимальные данные сессии в памяти браузера |
| Axios | HTTP-клиент браузера с таймаутом и приведением ошибок к общему формату |
| SCSS Modules и глобальные CSS-переменные | Локальные стили в `*.module.scss`, токены из DESIGN.MD |

Email и пароль живут в полях формы. В Zustand хранятся токен, идентификатор пользователя, роль и срок действия. После обновления страницы пользователь входит заново. На выходе и при истечении сессии очищаются Zustand и кэш приватных запросов. Пароль и токен не записываются в логи.

Запросы с данными аккаунта помечайте в TanStack Query через `meta: { private: true }`. Эта метка используется при очистке кэша сессии.

## Структура FSD

```text
frontend/
  src/
    app/                         # Маршруты, провайдеры и глобальные стили
      login/page.tsx
      account/page.tsx
      api/auth/login/route.ts
      styles/tokens.scss
    views/login/                 # Слой страниц FSD
    views/account/
    features/sign-in/            # Форма и мутация входа
    entities/session/            # Типы роли и сессии, Zustand
    shared/api/                  # Axios и типы ошибок транспорта
    shared/ui/                   # Кнопка и поля по мере переиспользования
```

`app` собирает маршруты и провайдеры. `views` выбран как имя слоя страниц FSD, чтобы не создавать каталог `src/pages`, зарезервированный Next.js для Pages Router. Импорты идут вниз по слоям `app → views → features → entities → shared`, через публичный интерфейс слайса. Слой `widgets` добавим, когда появятся самостоятельные составные блоки. [Структура Next.js](https://nextjs.org/docs/app/getting-started/project-structure)

## Как работает вход

1. На `/login` пользователь заполняет email и пароль. Форма проверяет обязательные поля и формат email, соблюдает клавиатурную навигацию и блокирует повторную отправку до ответа.
2. Axios отправляет `{ email, password }` в `POST /api/auth/login` на том же origin. Route Handler передаёт запрос в фиксированный `POST /api/v1/users/login`. Адрес Go API задаётся серверной переменной `API_BASE_URL`; локально используется `http://localhost:8080`. Ответ входа возвращается с `Cache-Control: no-store`. [Обработчик Go](../internal/api/handlers/user_handler.go) · [Route Handlers Next.js](https://nextjs.org/docs/app/getting-started/route-handlers)
3. Go находит аккаунт по email, проверяет пароль и возвращает `{ token }` с ролью аккаунта. Клиент читает `sub`, `role` и `exp` для интерфейса и проверяет формат данных и срок действия. Для доступа к защищённым операциям роль проверяет Go API. [JWT](../internal/auth/auth.go)
4. Если токен корректен, сохранить сессию, очистить пароль и перейти на `/account`. Минимальный экран аккаунта показывает роль и кнопку «Выйти». Без активной сессии он возвращает на `/login`.
5. Отобразить понятные состояния для `400`, неверных учётных данных `401`, недоступности сервера и ответа с некорректным токеном. Для `401` показать «Неверный email или пароль». Для сбоя соединения показать «Не удалось войти. Попробуйте ещё раз».

## Пошаговая реализация

### Шаг 1. Подготовить приложение

Создать `frontend/` с Next.js App Router и строгим TypeScript. Установить TanStack Query, Zustand, Axios и `sass`. Зафиксировать lock-файл и добавить скрипты `lint`, `typecheck` и `build`. Создать корневой layout, клиентский провайдер QueryClient и маршрут `/login`.

**Проверка.** После установки по lock-файлу проходят все три команды, а `/login` открывается локально.

### Шаг 2. Подключить дизайн-токены

Перенести переменные из [DESIGN.MD](../DESIGN.MD) в `frontend/src/app/styles/tokens.scss` и импортировать файл из корневого layout. Подключить стили экрана через `*.module.scss` рядом с компонентами.

**Проверка.** Сборка обрабатывает SCSS, экран получает общий фон и типографику, а режим уменьшенного движения обнуляет длительность переходов.

### Шаг 3. Собрать форму входа

Собрать страницу в `views/login`, форму — в `features/sign-in`. Добавить поля email и пароля, кнопку «Войти», клиентскую валидацию и место для общей ошибки. Проверить состояния ожидания и ошибки на подставных ответах.

**Проверка.** На узком экране форма помещается без горизонтальной прокрутки. Все элементы доступны с клавиатуры, ошибки связаны с полями, а во время запроса кнопка блокирует повторную отправку.

### Шаг 4. Подключить Go API

Создать `app/api/auth/login/route.ts` и описать `API_BASE_URL` в примере окружения фронтенда. Проксировать только запрос входа на фиксированный маршрут Go. В `shared/api` настроить Axios с таймаутом и привести ошибки транспорта к общему формату. В `features/sign-in` подключить мутацию TanStack Query без автоматических повторов.

**Проверка.** На запущенном Go API корректные данные возвращают токен. Неверный пароль и недоступность сервера показывают соответствующие сообщения из сценария входа.

### Шаг 5. Сохранить сессию и добавить выход

В `entities/session` описать две роли, проверку структуры и срока JWT и хранилище Zustand в памяти. Сохранять роль аккаунта из JWT в сессии. Собрать `/account` с ролью и кнопкой «Выйти». При выходе и истечении сессии очистить хранилище и кэш приватных запросов.

**Проверка.** Пассажир и водитель входят по email и паролю, а `/account` показывает роль их учётной записи. При некорректном токене форма показывает ошибку, сессия остаётся пустой. Выход, истечение сессии и обновление страницы аккаунта возвращают на `/login`.

### Шаг 6. Пройти сценарий и подключить CI

На работающем Go API пройти вход для обеих ролей, ошибку пароля, недоступность API и выход. Повторить проверку формы на узком экране, с клавиатуры и в режиме уменьшенного движения. Добавить в GitHub Actions отдельную задачу фронтенда с установкой по lock-файлу и запуском `lint`, `typecheck` и `build`.

**Проверка.** Локальный сценарий пройден, а задача CI запускает те же команды фронтенда.
