# Разработка и проверка Transfer Service

## Локальное окружение

Для `make check` нужны Go по версии из [go.mod](../go.mod), Make и C-компилятор для детектора гонок. Для проверки работающего API понадобятся Docker Compose и curl.

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт HTTP-сервера, по умолчанию `8080` |
| `DATABASE_URL` | Строка подключения к PostgreSQL. При запуске API проверяет соединение |
| `JWT_SECRET` | Случайный секрет подписи токенов, минимум 32 байта. Для локального запуска сгенерируйте значение командой `openssl rand -hex 32` и запишите его в игнорируемый `.env` |

В Docker Compose уже заданы локальные значения. При прямом запуске через `go run ./cmd/api` задайте переменные окружения или заполните локальный `.env` и заранее примените миграции. Значения секретов не включайте в коммиты.

## Проверка по типу изменения

| Изменение | Где проверять |
| --- | --- |
| Обработчик, валидация или код ответа | `go test ./internal/api/handlers`. Тесты используют HTTP-рекордеры и моки репозиториев |
| Хеширование паролей или создание JWT | `go test ./internal/auth`. Для правил доступа проверьте также middleware и регистрацию маршрута |
| Цикл фоновой очистки | `go test ./internal/worker`. Тест воркера использует подставной репозиторий |
| SQL, миграции или конкурентное бронирование | Запустите Compose с отдельной локальной БД и проверьте затронутый сценарий через API |

`make check` выполняет форматирование в режиме проверки, `go vet`, сборку и тесты с детектором гонок. CI использует эту же команду. Моки обработчиков и воркера не выполняют SQL.

В локальном Compose API и PostgreSQL слушают только loopback. Перед первым запуском задайте `JWT_SECRET` в `.env`. Смена JWT-секрета прекращает действие существующих сессий. Лимиты входа и регистрации действуют на адрес прямого подключения. За одним прокси клиенты делят этот лимит.

## Проверка работающего API

После `docker compose up --build` выполните `make smoke`. Цель проверяет `/health` и публичный список поездок. Запрос списка выполняет чтение из PostgreSQL. Для локального API на другом порту используйте `make smoke API_URL=http://localhost:8081`.

При изменении бронирования проверьте создание поездки водителем, бронирование пассажиром, уменьшение числа свободных мест и их возврат после отмены. Проверьте, что повторная отмена не увеличивает остаток. Для изменений воркера дождитесь истечения брони или выставьте прошлый `created_at` в тестовой БД и дождитесь следующего прохода очистки.

## Проверка перед пушем

После клонирования один раз выполните `git config --local core.hooksPath .githooks`. Установите зависимости фронтенда через `npm ci` в `frontend/`. Перед пушем запустите актуальный API через `docker compose up -d --build --wait` и проверьте затронутый пользовательский сценарий.

Hook проверяет чистоту рабочего дерева, наличие критичных файлов, Go-пакеты и сборку фронтенда. Последним запускается `make smoke` на локальном API. При ошибке Git останавливает пуш. Машинная проверка действует в клонах с включённым hook. Запрет на удаление самого репозитория зафиксирован в [AGENTS.md](../AGENTS.md), а право удаления на GitHub зависит от серверных разрешений.

## Миграции и Swagger

- Добавляйте изменения схемы новыми файлами в [migrations](../migrations) с секциями Goose `Up` и `Down`. Проверьте применение на пустой базе и обновление базы с предыдущей схемой, если изменение затрагивает существующие данные. В Compose миграции применяются перед запуском API.
- При изменении маршрута, тела запроса, роли или кода ответа сверяйте обработчик и его Swagger-аннотации. Из корня репозитория сгенерируйте `docs.go`, `swagger.json` и `swagger.yaml` в [docs/api/](api/) командой ниже. Исходники спецификации находятся в аннотациях Go.

```sh
go run github.com/swaggo/swag/cmd/swag@v1.16.6 init -g cmd/api/main.go -o docs/api
```

## Тестовая оплата Stripe

1. Возьмите секретный тестовый ключ `sk_test_…` в Stripe Sandbox. Запустите Stripe CLI командой `stripe listen --events checkout.session.completed --forward-to localhost:8080/api/v1/webhooks/stripe` и возьмите показанный секрет `whsec_…`. CLI должен использовать ту же песочницу. [Документация Stripe](https://docs.stripe.com/webhooks)
2. Перед запуском API задайте `STRIPE_TEST_KEY` и `STRIPE_WEBHOOK_SECRET` в окружении или локальном `.env`. При запуске через Compose экспортируйте их в окружение команды `docker compose up --build`. `STRIPE_RETURN_URL` по умолчанию указывает на `http://localhost:3000/bookings/payment-return`. Если ключ и секрет не заданы, оплата отключена.
3. Запустите фронтенд, создайте поездку с ценой от 0,50 USD и подайте заявку под аккаунтом пассажира и примите её под аккаунтом водителя. В списке броней нажмите «Оплатить в тестовом режиме». Checkout откроется в новой вкладке. Если браузер заблокирует её, воспользуйтесь ссылкой «Открыть Stripe Checkout». Для успешного платежа используйте `4242 4242 4242 4242`, будущий срок действия и любой трёхзначный CVC. Проверьте, что после вебхука исходная вкладка показывает подтверждённую бронь. [Тестовые карты](https://docs.stripe.com/testing)
4. Для проверки возврата откройте Checkout для другой брони, отмените её в исходной вкладке и затем завершите оплату в Checkout. Бронь должна остаться отменённой, а в Dashboard должен появиться тестовый возврат.

Для локальной проверки транзакций на PostgreSQL задайте `BOOKING_TEST_DATABASE_URL` и выполните `make test`. Тест применяет миграции во временной схеме и удаляет её после завершения.

Локальная очередь `stripe_refunds` сохраняет ожидающие возвраты. Воркер сверяет их со Stripe и фиксирует результат. Для `failed` или `requires_action` проверьте соответствующий PaymentIntent в Stripe Dashboard. Ошибки сети и Stripe API переобрабатываются с паузой.
