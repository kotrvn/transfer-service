# Роадмап Transfer Service

Учебная цель проекта — пройти полный цикл Go-разработки на сценарии бронирования поездки. Ближайший приоритет — проверить, что брони и остаток мест остаются согласованными в PostgreSQL. Подтверждение брони и тестовая оплата через Stripe реализованы, предстоит сквозная проверка в песочнице. Базовые сценарии водителя и пассажира уже реализованы во фронтенде.

## Что уже есть

- Unit-тесты обработчиков пользователей, поездок и броней, а также тесты авторизации и воркера.
- GitHub Actions для push и pull request в `main`. Локальный `make check` запускает тот же набор проверок. Обязательность проверок перед слиянием и автоматический деплой остаются отдельными задачами.
- Воркер раз в минуту переводит просроченные `pending` в `expired` и возвращает места в той же транзакции.
- Локальный запуск через Docker Compose, Swagger и `make smoke`. [Функциональность](features.md) · [Руководство по разработке](development.md)

## 1. Проверить бронирование на PostgreSQL

Начать с интеграционных тестов репозитория бронирований на отдельной PostgreSQL с применёнными миграциями. Это практика Go-тестов, транзакций и конкурентности на том же коде, который использует API.

- Бронирование уменьшает остаток, ручная отмена владельцем возвращает места.
- Попытка отменить чужую бронь оставляет статус и остаток прежними.
- При двух одновременных запросах на последнее место успешно создаётся одна бронь.
- Ручная отмена и фоновая очистка, запущенные одновременно для одной брони, возвращают места ровно один раз.

Этап готов, когда эти сценарии воспроизводятся локально и в CI. Unit-тесты дополняем при изменении валидации, прав доступа или HTTP-ответов.

## 2. Проверить тестовую оплату и подтверждение брони

Пассажир начинает оплату через `POST /api/v1/bookings/{id}/pay`. Подписанный вебхук Stripe переводит действующую бронь в `confirmed`. Повторная доставка сохраняет результат, оплата после отмены или истечения брони приводит к запросу возврата. Воркер работает с бронями в `pending`.

Остаётся пройти сквозной сценарий в Stripe Sandbox с тестовой картой, повторной доставкой вебхука и возвратом поздней оплаты. [Локальный запуск](development.md#тестовая-оплата-stripe)

## 3. Довести проверки и запуск до первого деплоя

- Подключить интеграционные тесты в обязательные проверки перед слиянием. Добавить GolangCI-Lint в Make и CI с небольшим согласованным набором правил.
- Передавать локальные значения через игнорируемый `.env`, добавить `.env.example` с безопасными заглушками. Для деплоя передавать секреты через окружение.
- Уточнить в Swagger коды и форматы ошибок затронутых маршрутов. Перед первым деплоем решить вопрос корректной остановки HTTP-сервера и воркера. Настроить автоматический деплой после выбора окружения.

## 4. Первый фронтенд — реализован

В `frontend/` на Next.js реализованы вход и регистрация с выбором роли. Водитель создаёт поездку из личного кабинета и отмечает её завершённой после подтверждений прибытия от пассажиров. Пассажир ищет поездки, бронирует места, видит статус брони и может её отменить. После бронирования и отмены интерфейс обновляет списки поездок и броней.

При включённой тестовой оплате пассажир может открыть Stripe Checkout из списка бронирований. [План фронтенда](frontend-plan.md) · [Визуальные правила и CSS-токены](../DESIGN.MD)

После завершения поездки стороны могут оценить друг друга. Рейтинг водителей отображается в поиске. Водитель видит рейтинг пассажира в заявке и может принять её или отклонить.

## 5. Расширять по мере необходимости

| Направление | Когда браться |
| --- | --- |
| Redis для `GET /api/v1/trips` | После замеров времени и нагрузки на запрос. Если кэш нужен, определить TTL и обновление данных при создании поездки, бронировании и отмене. Отдельно проверить актуальность `seats_available` |
| Чат на Go | После появления пользовательского сценария в интерфейсе и согласования прав доступа к переписке. Учебная цель — WebSocket между фронтендом и чат-сервисом, gRPC между чат-сервисом и API для проверки доступа |
